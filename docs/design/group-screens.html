Groups on every screen

The queue, the review page, the participants-page bulk form, the course report and the audit trail, reviewed with groups in them. Stages 1 and 2 gave every reviewed application a group and narrowed the deciders to theirs; this page proposes what each screen shows of that, and what the log keeps. Nothing here is built yet. The decisions it asks for are at the foot.

§01 · manage.php?id=

The queue: say whose application it is

What the queue shows today, for the three readers stage 2 created:

  • An unnarrowed decider (editing teacher, manager): every application of the method. A keyed one carries a blue badge with the key's outcome, for instance Key accepted, sent for review, and never the group's name (the cell comment says why: the mentee scope spans courses whose groups a mentor may not see).
  • A narrowed decider (separate groups, no moodle/site:accessallgroups): the applications whose newest record's key group is one of theirs, nothing keyless. In no group: core's notice “Sorry, but you need to be part of a group to see this page.” and no queue.
  • A viewer (viewapplications without manageapplications): the same narrowing, no selection column, no decision controls, no sticky footer, and You can view these applications but not decide them.

Nothing tells any of them which group a row belongs to, and nothing lets an unnarrowed teacher look at one group at a time. The filter row has search, status, the identity-field filters and the dates; the filterset declares no group filter.

Proposed: the narrowed decider's queue

The reader the owner asked for: a moderator in Turma A and Turma B of a separate-groups course, on a method in Key only, reviewed. Three additions: a Group column, a Group filter offering only their groups, and one line saying the queue is narrowed and to what.

The participants-page bulk form: narrowed already, and hard to reach

The form lists the selected applicants, the message and note boxes, and either the two choosers or, without choosedecision, one sentence: Each approval gives what its enrolment method sets: its groups (and the key's group, for an application a group key sent for review) and its role. You can approve or refuse, but not change them. Its group chooser is choosable_groups(), so a moderator is offered only their groups, and every row is re-checked by can_manage_application() inside the decision methods.

How a moderator gets here at all is the real finding. In a separate-groups course core's participants page shows a user without accessallgroups only the members of their own groups. An applicant joins a group on approval, never on application, so a pending applicant is in no group and does not appear on that page for the moderator. Only an applicant who is already a member of one of their groups (through another enrolment) can be selected there.

§04 · report.php and the custom-report source

The report: filter by group, and say what an approval joined

The course report already carries Admission route (with Key accepted, sent for review among its filter options, added in R1: checked) and Group of the enrolment key (named only where visible, not sortable). A narrowed viewreports holder already reads only the records whose key group or decided groups are theirs (S8). Missing: a way to pick a group, and the groups a decision joined.

What "decided groups" records is not what was joined

decidedgroups holds the decider's choice; empty means the method's defaults were used. A decider without choosedecision always records it empty, as does every approval left on the defaults and every approval from core's Edit enrolment screen. So for those approvals the record says nothing about the groups joined, and S8's narrowing (key group or decided groups) misses a keyless application the defaults put into Turma A. A column fed from this field would print an empty cell for most approvals. V-D10 proposes recording what add_instance_groups() actually joined.

§05 · T1

Today a decision leaves only core's events (user_enrolment_updated, role_assigned, group_member_added, and user_enrolment_deleted for a cancellation), none of which says "approved", "deferred" or by which method's rules; the record keeps the last decision only and is swept after 30 days by default. The plugin fires one event of its own, application_admitted_by_key.

Why "fire it in complete_approval()" is not enough on its own

complete_approval() is the one place every route into active passes, and the Edit enrolment route reaches it only through the hook, so the event belongs there. But it runs twice for a queue approval (the hook pass inside update_user_enrol(), then activate()'s own call), and it also runs for a key admission, which already logs application_admitted_by_key. Fired naively it logs every queue approval twice and every admission as an approval. Three routes, one event each:

  • Queue, review page, bulk: activate()'s own pass fires; the nested hook pass does not.
  • Core's Edit enrolment: the hook pass is not nested in activate(), so it fires.
  • Key admission: admit() suppresses it; its own event stands.

The marker must be request state, because enrol_get_plugin() returns a new object each call, so the hook's plugin is not activate()'s. It goes in classes/local/, not on the plugin class: validate fatals on a two-modifier member in lib.php on the 5.2 leg. It is set and cleared in finally, so no test inherits it.

// Sketch, classes/local/decisionlog.php (proposal).
final class decisionlog {
    /** @var array User enrolment ids whose approval event is owed by an outer caller. */
    private static array $owed = [];
    public static function defer(int $ueid, callable $run): void {
        self::$owed[$ueid] = true;
        try { $run(); } finally { unset(self::$owed[$ueid]); }
    }
    public static function is_owed(int $ueid): bool { return isset(self::$owed[$ueid]); }
}
// activate():  decisionlog::defer($ue->id, fn() => $this->update_user_enrol(...));
//              $this->complete_approval(...);                // fires, unless admit() wraps it
// admit():     decisionlog::defer($ueid, fn() => $this->activate(...));
// complete_approval(), after the writes: if (!decisionlog::is_owed($ueid)) { approved::create(...)->trigger(); }

One consequence stays: on the Edit enrolment route the event is triggered from a hook that runs before core writes the row, so a failed write would leave an "approved" log line behind. The notification already lives with the same order (its task re-reads the enrolment); the README says so.

The group menu of report_log filters on the group membership of the user who acted (userid), never of the affected user, and in separate groups a reader without accessallgroups is forced to the members of their own groups (or, in no group, to users in no group). For a moderator of Turma A that means:

  • A decision on a Turma A applicant taken by an editing teacher who is in no group is not shown to them. Applicants are no help either: they join the group only on approval.
  • A decision on a Turma B applicant taken by a colleague who moderates both A and B is shown, with the applicant's name in "Affected user". That is core's rule for every event; it is why the description carries ids and never a group name.
  • There is no event-name filter (the page takes course, group, user, date, activity, action, education level and origin), so the decisions cannot be listed alone; All changes plus Teaching narrows to them and much else.

So the log report does not help a moderator audit their group, and the course report remains their surface (V-D8: no link from the report to the logs). The events are the durable trail for an administrator and for anybody reading the log store through Report Builder, an export or a tool.

Privacy

  • Nothing to declare in the plugin's provider. The log store owns its table and declares it, with relateduserid and other among the fields; plugins that fire events (core's own enrol plugins included) declare nothing for them.
  • But the events outlive the plugin's own record. Core's standard log store exports rows where the subject acted or was affected, and on an erasure request deletes only the rows where the subject acted. An applicant's erasure therefore deletes their record and keeps the log lines about them, and the log's lifetime (logstore_standard | loglifetime, never by default) governs them, not Keep application records for. Core's own user_enrolment_updated already behaves exactly so, which is what makes it acceptable.
  • Hence other carries ids only: never the message to the applicant, the decision note, a group name or a role name. The README's privacy section gains one paragraph saying all of the above.

T2: is a history table still unnecessary?

For the audit, yes: the events record every decision, re-decisions included, with who, when, groups and role. What they do not give is a history on screen: no core page lists log rows by affected user and event. If the owner wants "decisions on this application" on the review page, the plugin can read its own events through core's log reader (\core\log\sql_reader::get_events_select(), relateduserid + objectid), with no table. It degrades to nothing when the standard log store is disabled or has purged the rows, and the panel would have to say so. A table only if that is not acceptable (V-D9).
