01

The custom label does something. On your site it just never gets the chance.

“Custom label — aparece apenas em apply/info.php, não consegui entender o benefício do campo.”

It has two readers, not one. It labels the applicant's comment box on the application form, and it retitles the comment column on info.php. Your observation is still correct about what you saw, and the reason is exact:

Measured on m502

The comment box is added only inside if ($instance->customint7) (classes/form/application_form.php:175) — the Commentary field switch, whose site default is 0 (settings.php:236). All six apply instances on m502 carry 0 there, so building the real form for the two instances that do carry a label produces no applydescription element at all. Those two instances hold zero comments between them; the two instances that hold comments carry no label. Today the setting retitles an empty column and nothing else.

Three things make it read as a mystery field

  1. The default never fires, and reviving it would be worse. edit_form.php:131 sets the default to the word “Comment”; set_data() at :249 overrides it whenever the stored value is a non-NULL scalar — including the empty string lib.php:1009 seeds. All six live rows are non-NULL, so on this site it has never pre-filled. It is not dead code in general: the column is nullable, and a NULL row lets it win. Leave it losing — if it ever pre-filled, saving the form would freeze the creator's own language string into {enrol}.customtext2, after which the label would never follow the language pack again. Empty is the correct default.
  2. Nothing ties it to the switch it depends on. No hideIf, no help button — so it renders live and editable on an instance where the thing it labels is switched off.
  3. In English it is invisible even when it works. comment and applycomment are both the word “Comment” (lang/en/enrol_apply.php:47,81), so on a default site a custom label changes nothing a reader would notice.
Two things to check before you decide

The column is historically polluted. Upstream stored the notification recipient list in customtext2 until 2016 (commit 3d27870), and this fork ships no migration for it. On a site upgraded from a pre-2016 build, the “custom label” may be carrying somebody's old recipient list.

And it is restore-controlled. restore_instance() sanitises customtext3, customint5 and customtext4 and leaves customtext2 alone, so its value arrives verbatim from a foreign archive. Both sinks escape today, which is why that is not a live hole — but with the non-default formatstringstriptags = 0 the escape flag is inert, and markup survives into the raw <th> and the raw triple stash alike.

What the setting is actually for

“Why do you want to join this course?” is a different question from “Which employer are you with?” Once a teacher has written that prompt, it should head the column of answers everywhere the answers are read — and today it heads exactly one listing, the one nothing links to prominently and which §02 recommends deleting.

A documented reason that is wrong

docs/design/implementation-plan.md:1221 and PROGRESS.md:457 both say the per-instance header is inexpressible in Report Builder because column::set_title() takes only a lang_string. The type is real (reportbuilder/classes/local/report/column.php:165, identical on 5.1 and 5.2) but it is not the obstacle — core's own $string['customfieldcolumn'] = '{$a}' passthrough carries arbitrary text through it. Recommendation

Keep it, and make it real — the cheap half first, which is worth doing under either answer: delete the dead setDefault, add hideIf('customtext2','customint7','eq',0), add a custom_label_help string to lang/en and lang/pt_br in lockstep. Then thread it into the review page's comment label, which holds $instance unconditionally, and into the queue heading on the ?id= scope only — the site-wide and mentee queues span instances and need a lang-string fallback, which is exactly the shape info.php already uses.

The sinks do not agree, and an earlier draft of this page said they did

Two of the three render raw and want the escaped spelling: the queue column header (flexible_table:1374 emits it through html_writer::tag, which never escapes its content) and the application form label (element-template.mustache:50, a triple stash). The review page's is a double stash (templates/review.mustache:124) and wants the plain spelling. Put the switch in one helper taking an $escape flag, the way core's own field_controller::get_formatted_name() does, rather than deciding it at three call sites. And note what holds this today: nothing. There is no assertion anywhere on the queue's comment column header — measured, zero matches in the renderer and sort-order tests — so the split needs its own test in the same change.

The deletion blocker is not the one the design docs record

Delete outright unless you know FUNDASEG has it bookmarked.

03

The queue: rebuild it, but not on Report Builder

“…precisa respeitar as configurações showuseridentity. Faltam elementos que ajudem a definir se o usuário pode ou não ser aprovado… O nome do usuário deveria ter um link para o perfil… Filtro por letra não é necessário… campo de busca ajax por nome com accent-insensitive… tabela responsiva… paginação e lazy loading… filtros por campo de perfil requisitado… incluindo vagas remanescentes.”

The obvious move is to reuse the Report Builder system report this plugin already ships. It is the wrong move, and the reason is a measurement rather than a preference.

Why not Report Builder

course_applications's main table is enrol_apply_submission. The queue's subject is {user_enrolments}, and they are not the same row set. Measured on live m502 just now: six applications awaiting a decision, and one of them (ue=357) has no submission row at all — while 21 of the 27 submission rows point at a user enrolment that no longer exists. The two sets diverge in both directions. One row is enough to make the point, and the gap is structural rather than incidental: an application approved before the record existed and later suspended from the participants page never gets one, and neither does a restore from an archive older than the trail. A Report Builder queue would silently under-report exactly those, which is the failure mode this repository treats as the defect. Report Builder also hardcodes its checkbox group to report-select-all (system_report.php:179), and core's only precedent for turning that into a bulk action scrapes the checked boxes into a hidden input with JavaScript — which would destroy this plugin's deliberately no-JavaScript queue and the CSS sticky-footer polyfill that protects it.

Build a plugin-owned core_table\dynamic table instead — \enrol_apply\table\applications plus its filterset, keeping {user_enrolments} as the main table and keeping the existing POST contract. That surface gives AJAX paging, sorting, page size and a setFilters() channel for the search box, and paging and sorting still degrade to ordinary GET navigation with JavaScript off, because the dynamic module intercepts real anchors and the paging bar emits real hrefs.

Three things to design for before writing a line of it

1. The filters do not degrade. setFilters exists only in JavaScript; there is no GET encoding of a filterset anywhere, unlike tsort/tdir for sorting. So the no-JS story is paging and sorting, not filtering — keep a plain GET search as the fallback.

2. The web service builds the table with one argument. It constructs new $tableclass($uniqueid) and then applies the filterset, so the scope arrives from the client. And the dynamic interface declares exactly one has_capability(), checked once against one get_context() — while this queue has three scopes across two context levels. The instance id, the mentee restriction and the authorisation must all be re-derived server-side from the filterset on every request, exactly as course_applications::can_view() already does for the report. This is the single largest correctness risk in the rebuild.

3. There is no plugin precedent. Every core implementor of core_table\dynamic is a core subsystem — participants, Report Builder, plugin management, SMS. The resolution in get.php is generic (\<component>\table\<handler>), so a plugin can do it; nobody in core has.

Two things the current queue gets wrong, before any redesign

Measured on m502 — a disclosure

The queue prints every applicant's e-mail address unconditionally, consulting neither showuseridentity nor hiddenuserfields. On this site showuseridentity names only username — which is what keeps the e-mail column off core's participants page — and hiddenuserfields lists email as well. The queue beside it prints the address anyway. That is your showuseridentity request, and it is a live defect rather than a missing feature.

Measured on m502 — an invisible filter

The initials filter stays live even when the bar is not drawn. Rendering with out(50, false) hides the control and nothing else: with a stored i_first = 'Z' the same queue went from 3 rows to 0, with no bar on the page and nothing to explain it. Hiding the bar is not removing the filter — the complete kill is overriding get_sql_where() to return ['', []]. (Emptying $userfullnamecolumns also works and silently costs the fullname column its firstname/lastname sub-sort links.)

Your requirements, costed

RequirementCostMechanism, and what it really costs
Respect showuseridentitylow fields::get_identity_fields($context) for the list and fields::get_sql() for the SELECT and the custom-field joins. It also honours hiddenuserfields, which is the half that is broken today. Two traps: pass $namedparams = true or fix_sql_params() throws mixedtypesqlparam (the queue's existing for_userpic() call discards params and joins, so it is not a template for this); and the custom-field join it emits is an INNER join on {user_info_field}, so a configured identity field that no longer exists empties the entire queue.

Paginationfree Already there, and AJAX on a dynamic table.
Responsive / mobilemedium Not free on any surface. A Mustache rewrite of the row into a card layout — which is why identity belongs on a sub-line rather than in columns.
AJAX search by namemedium One AMD module posting to setFilters(). Server side, users_search_sql() gives core's own semantics over fullname, e-mail, idnumber and the identity fields.
Accent-insensitivemedium — and honest about it Not portable. MariaDB gets it from the collation for nothing; PostgreSQL does not, and core says so itself: “postgresql does not support accent insensitive text comparisons, sorry” (pgsql_native_moodle_database.php:1480, both branches). The unaccent route local_dimensions uses works, but the extension exists on m502 only because local_dimensions installed it, and the CI PostgreSQL image has the files and no created extension. A test can provision it for itself — the CREATE EXTENSION is visible for the rest of the test and rolled back after, which is exactly what local_dimensions's own test does, provisioning and skipping only if that fails. So this is testable; what it is not is uniform. Ship it as best-effort with a documented fallback, or match core's participants search and say plainly that PostgreSQL sites match accent-sensitively. Note the queue already diverges this way today: the initials bar asks for accent-insensitive matching and gets it on MariaDB only.
Filters by requested profile fieldblocked Not achievable as stated. The snapshot is one TEXT column holding a JSON array, so getting one field is a path search rather than a key lookup — and Moodle's DML exposes no JSON abstraction at all, so it needs engine-specific SQL behind a get_dbfamily() guard and can use no index either way. (The empty string that 18 of 27 live rows hold would also throw a PostgreSQL ::jsonb cast, but that part is trivially guarded — it is the portability and the missing index that block it.) This needs the deferred enrol_apply_submission_field child table (slice 10). Nothing about the chosen surface changes that.
Lazy loading / infinite scrollhigh, and it fights the bulk bar Core does ship a primitive — scrollBottom in core/custom_interaction_events (:40, :304-318, :543) — with two live consumers, both in the message drawer. But it is jQuery-based, which this fleet forbids in new code, no core table uses it, and it contradicts the selection model: a refresh replaces the whole table region, so rows scrolled past would lose their checkboxes. AJAX paging with a large page size and a real search is the answer that survives contact with a bulk decision — which is what both mockups show.
Details in a modalmedium Core has no user-profile modal to reuse — the only details modal on a user list is core_user/status_details, and that is enrolment details built from data attributes. Build a core/fragment callback rendering the frozen snapshot plus the identity fields — which is also the safe answer, because it reads nothing live. The plain profile link is the fallback.
The cheap path, if you want most of it this week

Everything except AJAX search and lazy loading is reachable on the existing table_sql without changing the surface at all — identity fields, killing the initials filter, the profile link, the capacity header, the snapshot column, and a plain <form method="get"> search using users_search_sql(). That is about a day, no new classes, no AMD, no Behat locator churn — and it removes the e-mail disclosure now rather than after a rewrite. The dynamic-table rebuild then becomes an upgrade rather than a prerequisite.

Measured on m502 (?userenrol=395): the applicant's name is rendered twice — once as the page heading, once as an h2 — and what sits between them is worse than the repetition. There is no breadcrumb, and no back-to-queue link. The page <title> is “Enrol Confirm”, which names neither the applicant nor the course.

The thing between the two headings

The review page renders the site front page's secondary navigation. Eight links, every one of them pointing at course id 1 rather than at the course the application was made to. The cause is one missing call: the review branch runs require_login() with no course (manage.php:47) and then sets the context at :122, but never $PAGE->set_course() — so $COURSE stays the site course and every navigation node is built from it. That is also why there is no breadcrumb: core would render one, and does build the navbar object, but the theme suppresses it on a page whose course is the site.

And the two panels contradict each other

The snapshot panel is masked in the course context, so a mentor — the audience require_review_access() exists to serve through the applicant's user context — gets only the six name keys and loses city, institution, phone and every custom field. The e-mail row three lines above it is an identity field too, and it is printed unconditionally. One panel withholds what the other prints, on the same page, to the same reader.

Where the duplicate comes from

user/index.php:251 loops over enrolment instances, and calls $plugin->get_bulk_operations($manager) inside that loop (:257) — on the same plugin object every time, with a manager carrying no instance filter. The url it builds is ['plugin' => 'apply', 'operation' => $key] and nothing else (:261), and it appends a fresh optgroup labelled with the plugin name (:266-267). N apply instances therefore produce N byte-identical optgroups: same label, same three option values. The file is byte-identical on 5.1 and 5.2.

Measured on m502

Course 2 already carries two enabled apply instances (“IMA 1”, “IMA 2”) and renders two identical <optgroup label="Course enrol confirmation"> blocks. Stock core does the same thing: adding three enrol_self instances to a generated course gives four Self enrolment optgroups — four, because get_enrolment_instances() defaults to including disabled instances and a disabled one produces an optgroup exactly like an enabled one. enrol_manual escapes the whole thing only because its can_add_instance() forbids a second instance. So this is core's loop, not this plugin's — and get_bulk_operations() cannot know which iteration it is on.

A candidate can hold two applications in one course at the same time. The lock in submit_application() is keyed on the instance and the user, not the course. Measured: both calls returned created, two user_enrolments rows, two enrol_apply_submission rows — and after applying to IMA 1, the enrolment page still rendered a live apply button for IMA 2. Two clicks reach the state.

Honest, because the duplicate entries are the same link. Two questions you asked inside item 3

“Defer requests”, and enrolling with no role

What deferring actually does

It moves a pending application into a third status only this plugin understands. For the manager it is coherent and complete. For the applicant it is invisible.

It doesMechanism, measured on m501 and m502 alike
Writes status 2 ENROL_APPLY_USER_WAIT, this plugin's extension of a column core defines two values for. Core tests != ENROL_USER_ACTIVE everywhere, so it is inert to core.
Clears the expiry to the integer 0, leaves timestart alone lib.php:1203. Without it a once-approved row lands on the waiting list carrying a past timeend — a state no sweep touches and no queue lists.
Keeps the applicant's comment unlike approve and cancel, which delete the applicationinfo row.
Stays in the queue and stays decidable the predicate is “not active and not expired”. Confirm and cancel accept status 1 or 2 (lib.php:1286); defer accepts 1 only.
Frees the place, keeps the applicant slot places_taken() counts ACTIVE rows only; applicants() counts every non-expired row. Measured before and after a deferral: applicants 1 → 1, places taken 0 → 0.

So deferral is the overflow bucket inside the applicant cap: “considered, not given a place, still decidable.” That is a defensible feature. It is not, however, a waiting list in the sense its own label, heading and notification all claim — and here is why.

Three defects, all measured

1. The applicant is never told. The words “waiting list” reach no applicant-facing surface. enrol_page_hook() branches only on does a row exist (lib.php:213-215), so pending and deferred applicants are shown the identical “Enrolment application successfully sent…”. Verified by calling the hook as the applicant on both branches. applied.php:40 gates on the same row-exists test with no status clause, so it too tells a deferred applicant their application “is waiting for a decision”.

2. The one notification it does send is blank on the web. All six subject and body settings ship as the empty string (settings.php:76-132), and e-mail is enabled by default for every provider (db/messages.php). On the live m502 site, 14 of 14 applicant-facing notifications ever sent have an empty subject and 10 of 14 an empty body — while the 34 notifications sent to managers over the same period all have both, because that one is built from the plugin's own Mustache template rather than from an empty admin setting. The plugin writes the message it composes itself and ships nothing for the three it asks an administrator to write. The class does set a smallmessage that says the right thing, and the notification drawer does not render it — it renders shortenedsubject (message/output/popup/templates/notification_content_item.mustache:67), so the drawer entry is blank. The exception is worth knowing rather than glossing: message_output_airnotifier does read smallmessage, so on a site with the mobile app configured the applicant's phone shows the correct sentence while their web notification and their e-mail show nothing.

3. Nothing promotes from it. No position, no ordering, no automation. A place freeing triggers nothing — sync_enrolments calls only process_expirations().

4. And it turns “Maximum applicants” into a lifetime total. This is the one to fix first. applicants() counts every non-expired row, a deferred row carries timeend = 0 by design, and process_expirations() selects on timeend > 0 — so a deferred application counts against customint3 for ever. Nothing promotes it, nothing ages it out, and the applicant cannot withdraw: get_unenrolself_link() requires status = ENROL_USER_ACTIVE (lib/enrollib.php:2517, same on both branches, read in full). The only release valve is a manager cancelling by hand. Defer a course's whole queue and it stops accepting applications, with nothing on any screen able to say why. That is the same ratchet shape PR #54 fixed on the places cap, arrived at from the applicant side.

And a fourth, smaller: pressing Defer on an already-deferred application is a silent no-op reported as “Applications updated”. The participants-page bulk path counts and reports unchanged rows correctly (decision_operation.php:216); the queue and the review page do not.

Recommendation on deferral

Decide what it is for, then finish it or rename it. Two cheap fixes are worth doing under either answer: give the three applicant notifications a non-empty default (fall back to a lang string when the setting is blank), and add a third branch to enrol_page_hook() that reads the status and tells a deferred applicant where they stand. Move that branch ahead of allow_apply() while you are there: today, once an instance stops accepting new applications, somebody who already applied is told “Enrolment is disabled or inactive” — a message about somebody else's problem.

The ratchet needs its own answer and it is not cosmetic. Three ways out, in increasing order of how much they change: let the manager see the deferred share of the applicant count so cancelling is an obvious move; give the applicant a way to withdraw, which core's own self-unenrol link cannot provide for a non-active row; or make the cap concurrent by ageing deferred applications out. The first is a day's work and buys most of it.

Enrolling with no role — correct, and it is core's own rule

An application has to be recorded somewhere, and {user_enrolments} is the only table core gives an enrolment plugin. So apply() writes a suspended enrolment with roleid null (lib.php:284); the role arrives on approval in complete_approval().

Why — measured on both branches

has_capability() never consults the enrolment at all; whether somebody may enter the course is a separate test, and core ships two of those with opposite defaults. require_login($course) reaches enrol_get_enrolment_end(), whose SQL demands ue.status = ENROL_USER_ACTIVE, and refuses a suspended row; can_access_course() defaults $onlyactive = false and admits it — the same trap this repo already documents for the review page's own gate. So a pending applicant is not invisible everywhere: measured, a course-level calendar event is visible to a pending and to a deferred applicant and not to an unrelated logged-in user. What the role governs is the capability half, and there the difference is total. Measured with a suspended enrolment carrying the Student role: has_capability() yes, get_users_by_capability() yes, get_gradable_users() yes, get_enrolled_users($ctx, 'mod/quiz:attempt') yes, listed by get_role_users() as a Student. With no role: none of them. A pending applicant can do exactly one thing — appear on the participants page as a Suspended row with no roles, which is what lets a teacher find them.

Core says so itself, in core's own words: “Only active users in enabled instances are supposed to have roles” — enrol/meta/locallib.php:183, the same line on 5.1 and 5.2, with three core enrol plugins shipping the identical call. There is a fourth cost too: core passes a component only when roles_protected() is true, which this plugin returns false for, so a role assigned by enrol_user() would be unstamped and core could not clean it up precisely.

Leave it exactly as it is. What is worth fixing is not the mechanism but the vocabulary: an administrator reading the setting “Role assigned to a user…” has no way to know it means on approval — which is precisely where this question came from.

Decided

All nine were answered on 31 August 2026. Recorded here so nothing below reads as still open; the implementation plan is built on exactly these.

QuestionAnswer
What is deferral for? A triage state, not a waiting list. Approved means the criteria were met and the applicant is enrolled; rejected means they were not, and there is no queue to sit in. Deferred means all or part of the criteria were met and the application is waiting either for a place (new ones, or an approved applicant dropping out) or for something to be validated. It becomes its own filterable status, and the decider gets a field to record the reason so the trail survives. No automatic enrolment when places free.
Is a second apply instance in one course supported? Yes. A new intake, a new class, a teacher reusing a course. Not ideal practice, but common — so the bulk path has to cope with it rather than assume it away.
Two pending applications by one person in one course? Allowed. Which makes the silent partial bulk decision the reachable case, not the edge one.
As-you-type search versus no-JavaScript? Search as you type, backed by a web service, built the way local_dimensions builds its own: an ajax => true external function called through core/ajax, matching with sql_like_ai(), capped and reporting overflow. The no-JavaScript path keeps paging, sorting and a plain GET search box.
Accent-insensitive on PostgreSQL? Best-effort — unaccent where the extension exists, documented fallback where it does not.
Which context judges showuseridentity? Identity columns on the ?id= and site-wide scopes only, never the mentee scope.
Prior applications on the review page? Yes, gated on enrol/apply:viewreports.
Schedule slice 10 (the per-field child table)? No. Filters by requested profile field stay out of scope, and the queue must not imply they exist.
info.php? Delete outright. No redirect stub.
The polluted customtext2? Clean it in an upgrade step; a CHANGELOG entry is all the record it needs.
Mockups? A (the triage queue) and C (the rebuilt review page) are approved. No details modal — the applicant name is a plain profile link. Lazy loading resolves to AJAX paging with a large page size and a real search.
The one thing the answers left ambiguous, and how it was read

“Search as you type, displayed dynamically below” can mean a suggestion dropdown under the box (which is the widget local_dimensions uses — core/form-autocomplete with a custom transport) or the table itself narrowing as you type. Mockup A is approved and shows the second: a filter box with removable chips above a table that re-renders. That is what the plan builds, because a picker narrows to one person and defeats bulk triage. The server side is identical either way, so a suggestion dropdown remains an additive change on the same web service if it is wanted later.
