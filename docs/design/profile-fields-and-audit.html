enrol_apply · architecture proposal

Profile fields, done right

Today the two profile options dump the entire user-editing page underneath the title of the enrolment method — twice, if there are two methods. This proposal replaces that with an explicit choice of fields, a review screen of its own, real saving into the profile, an auditable JSON snapshot, a report through Report Builder and the cohort restriction that Self enrolment already has.

01 — Diagnosis

What is wrong today

customint1 and customint2 switch on two whole, indivisible blocks. useredit_shared_definition() is all‑or‑nothing: along with city and phone come the email display selector, timezone, theme, the description editor, the profile picture filemanager and the interest tags. profile_definition() takes no field filter — it renders every custom profile field, or none.

And none of it is saved. The values only travel into the notification email. Worse: the custom fields the approver receives come from the database, not from the form — profile_load_custom_fields() at lib.php:700 — so what the applicant typed never reaches anyone.

Measured, not assumed

With two methods enabled, the page today emits id_firstname, id_description_editor, id_imagefile, id_category_N and twenty more identical ids twice — including the name of the hidden field mform_isexpanded_id_moodle_picture. Clicking the “First name” label on the second card focuses the first card's field. That is a WCAG 1.3.1/4.1.1 failure, on top of two TinyMCE instances and two file pickers fighting over the same ids.

02 — Schema

The discovery that changes the design

Storing userinfodata as JSON is the right idea. The place is what does not work: the enrol_apply_applicationinfo row is deleted on approval. 

// lib.php:241, inside complete_approval()
$DB->delete_records('enrol_apply_applicationinfo', ['userenrolmentid' => $userenrolmentid]);

And on cancellation too (lib.php:598) and in unenrol_user() (lib.php:899). On top of that, hook_callbacks.php:68 uses the existence of that row as proof that a status change to active was an approval and not an ordinary enrolment edit: 

// classes/hook_callbacks.php:68
if (!$DB->record_exists('enrol_apply_applicationinfo', ['userenrolmentid' => $userenrolment->id])) {
    return;
}
Consequence

A snapshot stored there destroys itself at exactly the moment it acquires audit value. And if the row stops being deleted in order to preserve it, complete_approval() starts firing again on every status edit of an already approved user — rewriting groups and requeueing the confirmation message.

The fix: its own column, in a row that survives

enrol_apply_applicationinfo stays untouched — the hook's marker keeps working and none of the four deletion paths changes. The userinfodata column moves to a new, durable table, written in the same transaction. The queue and the notification read it through a join. Duplicating the JSON across both tables was considered and discarded: it would be a second copy whose only defence would be a test created to police the redundancy the design itself introduced.

The key cannot be userenrolmentid

It was the first thing the design tried, and it is fatal. unenrol_user() (lib.php:891‑903) deletes by that key, and cancel_applications() (lib.php:597‑598) calls unenrol_user(). A “cancelled” audit entry would be destroyed by the very cancellation it exists to record; an “approved” one, by any later unenrolment.

The key is courseid + userid (plus enrolid for convenience). That also changes the backup: annotate_ids('user', 'userid') and annotate_ids('user', 'decidedby'), resolving through core's user mapping — and not reusing the enrol_apply_userenrolment one the plugin registers today (lib.php:936‑959).

Proposed schema

NEW enrol_apply_submission          -- durable: updated on decision, never deleted
  id
  courseid  int   -- the ONLY key that survives until the course_deleted event
  userid    int
  enrolid   int
  userenrolmentid int   -- reference only; NEVER the key to anything
  comment
  userinfodata     text  -- the snapshot, as JSON
  status           int   -- 0 pending · 1 approved · 2 waiting · 3 cancelled
  timecreated, timedecided, decidedby
  UNIQUE (courseid, userid)  -- without this, "one row per application" is just a phrase (see below)

NEW enrol_apply_submission_field    -- slice 9, deferred: zero SQL over JSON in the report
  submissionid, sortorder
  userid      int        -- denormalised ON PURPOSE (see the privacy box)
  fieldkey    char 100   -- 's_city' | 'c_7'
  fieldsource, fieldid
  fieldlabel  text       -- label FROZEN at submission time (text, not char 255)
  fielddatatype
  fieldvisible int       -- PROFILE_VISIBLE_* frozen
  state       char 20    -- confirmed | updated | declined | prefilled | locked | blocked
  valuebefore, valueafter, timeconfirmed

The child table is deferred (slice 9), but the ground is prepared now: the JSON envelope is versioned and carries label, type, visibility, state and values per field, so that the child can be backfilled from it in an upgrade step, with no painful migration. And the state vocabulary lives in a class constant from the start — not in a comment.

The userid on the child table is not convenience

Core's privacy compliance test only forces the declaration of tables that have a column literally named userid or a single-column foreign key to {user}.id — privacy/tests/privacy/provider_test.php:245‑266, used at :293‑315.

Without that column, the table holding the actual profile values — the most sensitive one in the whole design — is not forced, and forgetting its provider would pass CI green. A denormalised userid turns core's safety net into something that actually catches.

No denormalised counters. A report that disagrees with its own detail rows is worse than a slow report — Report Builder's aggregation handles it.

Mask by availability, not by callback

The temptation is to mask sensitive values in the column's add_callback(), row by row. That protects nothing. Filtering and sorting are SQL and never go through a callback: anyone building a custom report recovers a value they cannot see by adding a text filter (“valueafter contains X”) and reading the row count, or simply by sorting on the column. And under aggregation the callback receives nulls, because column::get_fields() collapses the aggregated column into a single field.

The correct model is core's own: decide once, with set_is_available(), on the column and the filter and the condition. And the masking applies to every row of a masked field, never only those that hold a value — a marker that appears only where there is data is a presence oracle, a defect local_groupdist has already shipped and fixed (CHANGELOG.md:229‑233).

Frozen vs live. Label, type, visibility level, values and state are frozen at write time — so deleting a custom field does not delete its history. What is evaluated live is only whether the reader holds the capability, and that evaluation happens when the report is assembled, not per row.

A race between two tabs

“One row per application” is an assertion, not a guarantee. Two simultaneous submissions both pass the already‑applied record_exists and both reach apply(). Today the foreign‑unique key on applicationinfo makes the second insert blow up; the new table needs a unique key of its own. The customint3 places cap (lib.php:150‑156) has the same race and deserves a short lock around apply().

03 — Flow

One form class, two transports

The “second page or modal” request needs no decision: core already covers both with the same code. single_button renders a real <form>; with JavaScript, the AMD module intercepts the click and opens the same class in a modal.

  1. Card on enrol/index.php

    enrol_page_hook() returns an enrol_page with a heading, the explanatory text (customtext1 + “you are about to check N details”) and a button to /enrol/apply/apply.php?instance=N.

  2. Modal, when JavaScript is there

    enrol_apply/enrol_page opens core_form/modalform with \enrol_apply\form\application_form. Without JavaScript the button navigates to the page — same class, rendered outside AJAX.

  3. Checking the fields

    set_data_for_dynamic_submission() pre‑loads the user's current values and those of the chosen custom fields — it is what makes the screen show “what is already there”. Today that pre‑load is $mform->setDefaults((array) $USER) in apply_form.php:105, and it goes away with the file.

  4. Saving and snapshot

    Profile saved in core's canonical order, then apply() — the single write point for an application (lib.php:201‑232) — with both inserts in one transaction.

  5. Acknowledgement page

    /enrol/apply/applied.php: plain require_login(), checks that the current user really does have a user enrolment on that instance — otherwise it is a free page telling strangers the instance exists — and never /course/view.php, which bounces a suspended user straight back. This is where the offer “Save these profile details for future applications?” appears, and only when there is a real difference between what was typed and the live profile (§5).

Locked field: three states, not two

The rule “what the user cannot edit does not appear at all” needs a third bucket, or it turns into a leak. This plugin already e‑mails profile fields to the approver; hiding a field from the screen and snapshotting it and passing it on anyway is disclosing a value the applicant never saw.

The “absent” bucket is the one a two‑bucket design gets wrong: a PROFILE_VISIBLE_NONE field is invisible to its own owner, and lang is never editable by a real user. Those are values the applicant has nowhere to read anywhere in Moodle. Note that core's answer to a locked field is the opposite of hiding it: hardFreeze() renders label and value with no input.

Decide before the addElement — do not hide afterwards

required rules are attached when the element is created, and HTML_QuickForm::validate() walks $_rules by name, without checking whether the element still exists. Any “add then remove” technique, or hiding with CSS, leaves the form permanently unsubmittable with no visible field to explain why.

And do not call useredit_shared_definition() at all: it adds four section headings unconditionally, before and independently of the fields. On an SSO site where everything is locked, the result is an accordion of empty sections.

The red does not come for free

The red marker in element-template.mustache comes from {{#required}}, which is switched on by addRule(..., 'required', ...) and appears on every required field — filled in or not. And .invalid-feedback only paints after a rejected POST. In other words: on the first render, a required field that is filled in and one that is empty look identical.

So it is two things, not a choice between them: addRule for the marker and the check in validation() to make it stick (a client‑side rule never blocks a POST) — plus a treatment of its own for “empty right now”, which is what you asked for. That brings the fleet's CSS rules with it: theme tokens with a var(--bs-*, var(--*, …)) chain, no !important, and correct dark mode.

A new hole the design has to close

enrol/index.php:63‑65 refuses any enrolment during a “log in as” session (loginasnoenrol). Today that file is the only way into the form — enrol_page_hook() has no other caller anywhere in core.

The two new routes — the apply.php page and the web service core_form_dynamic_form (ajax => true) — do not go through it. Without the guard reproduced in both, an administrator logged in as somebody else submits an application in their name. enrol_self's own form has that flaw, so copying it verbatim inherits it.

The detail that makes the modal work

The final constructor of dynamic_form runs external_api::validate_context(), which ends in require_login(). For an applicant not yet enrolled that throws require_login_exception('Not enrolled') — the modal would fail for exactly the people it exists for. That is why both of core's enrolment forms return the category context, not the course one, and say so in a comment.

Since the category is a context where this plugin declares no capability at all (db/access.php is entirely CONTEXT_COURSE), check_access_for_dynamic_submission() resolves the instance by id server‑side and re‑evaluates everything in the course context: “log in as”, isguestuser(), can_view_course_info(), allow_apply(), already‑applied and the customint3 cap.

Two cautions on the CTA

“Never redirects to /user/edit.php” is not a promise the plugin can make. require_login() redirects there whenever user_not_fully_set_up() — and every home destination except the site home goes through require_login(). The honest sentence is: the plugin never redirects there.

And defaulthomepage can point somewhere the applicant cannot get into. get_default_home_page_url() accepts any local path — /course/view.php?id=N included. The right route is get_home_page() plus the whole integer→URL mapping copied from login/lib.php:356‑372, with a fallback to / in the HOMEPAGE_URL case. Do not call core_login_get_return_url() (it clears $SESSION->wantsurl) or user_get_default_homepage_options() (it only exists on 5.2).

A detail easily lost in the rewrite: the comment field (customint7 with a label from customtext2, today in apply_form.php:85‑92) has to move to the new form — manage_table.php:93 and info_table.php:66 still read ai.comment. And its label becomes the escaped spelling, because a moodleform label renders in {{{label}}}; today apply_form.php:88 uses the plain one.

04 — Configuration

Choosing the fields, at two levels

The site level defines what a teacher may choose; the instance level defines what they chose. This is not bureaucracy: it is what makes writing to the profile safe, because the allowed set is recomputed on the server on every read.

The site setting's default is load-bearing, not a detail

admin_setting_configmulticheckbox stores only the ticked keys. If the default comes out empty, the intersection in resolve() zeroes everything and every migrated instance stops collecting the fields it collected before the upgrade — no error, no warning. And the precedent being copied, showuseridentity, defaults to ['email' => 1]… and email is on this proposal's hard exclusion list. The default has to be declared explicitly and seeded by the upgrade step itself, with a test that upgrades a customint1=1 instance on a site where allowedfields was never written and asserts that the fields still resolve.

Key vocabulary

Standard s_<column>, custom c_<user_info_field.id>. Id, not shortname: user_info_field has no unique index on shortname and core compares shortnames case-insensitively ($DB->sql_equal(..., false)) — renaming a field would silently re-point the choice. The profileoption the plugin already has today stores an id, so this is consistency, not invention.

Default set = \core_user::AUTHSYNCFIELDS (17 names, byte for byte identical on both branches) minus four exclusions, which gives 13 keys. Against what core actually renders in user/editlib.php, that is 12 plain text fields and one select (country) — not “nine, seven of them text”. Worth writing the list as an explicit constant rather than deriving it, so that the configuration and the renderer cannot drift apart.

ExcludedMeasured reason
emailWith authloginviaemail the email address is the login identifier; changing it is a flow of its own, with confirmation. A self‑service rewrite on an enrolment screen is account-takeover surface.
idnumberAccount-matching key for tool_uploaduser and external sync — and it is PARAM_RAW, not PARAM_TEXT.

Two warnings about the list. The four phonetic/middle/alternate name fields are still subject to useredit_get_enabled_name_fields(): if $CFG->fullnamedisplay does not use them, they drop out of the set. And url is not included because it does not exist — it became a social field in Moodle 4.0. It is dead in renderer.php's constant and should go in the same commit.

What has to be retired alongside it

show_standard_user_profile and show_extra_user_profile (settings at settings.php:200‑214, feeding get_instance_defaults() at lib.php:445‑446) become dead configuration that still seeds retired columns into every new instance. They come out of settings.php, out of lib.php and out of both language tables in the same commit — CI's validate step reads the alphabetical ordering, so half a removal fails.

And there is a decision to take about profileoption: today it offers any text field (settings.php:39‑52) and prints it in the queue (manage_table.php:100‑108, :247‑249) with no visibility check at all. With the new field picker there would be two unrelated mechanisms for “show a profile field in the queue”, and the old one is the one that leaks. Either it is retired in favour of the chosen set, or it goes through the same visibility helper.

05 — Security

Optional write and the data lifecycle

Owner's decision · the optional button

The silent write is gone. The applicant submits the application and, on the receipt page, is offered: “Save the profile data for future applications?” → [Update profile].

That changes the design for the better — the write becomes explicit and user-initiated. But it does not change a line of the security obligations below: the validation is owed by the write, not by the widget.

Literally as asked: it cannot be done

/user/edit.php accepts four parameters — id, course, returnto, cancelemailchange (user/edit.php:32‑35, identical on both branches) — and none of them carries a field value. $user is read from {user} and enriched only from server-side sources; the form ends in set_data($user). There is no hook, session key or draft: user/ dispatches six hooks and none of them touches the edit form.

And returnto is PARAM_ALPHA tested against the literal 'profile' — there is no arbitrary return URL. After saving, the applicant lands on their own profile or on their preferences, never back in the course.

The shape that works

A page of the plugin's own (/enrol/apply/profile.php?instance=N) showing the difference between what was typed and the live profile → the button writes → the button itself turns into “Profile updated” and the CTA leads to the configured home. No trip to the profile page. The mockup is in §3.

Two findings that change the screen

1. The button is inert in the common case. Today's form is pre‑filled from $USER (apply_form.php:105): anyone who edited nothing posts back their own record. Without a diff, the page lists the data the user already has and asks permission to save it. It has to compare against the live record, show only what changed and hide the button when the delta is empty.

2. Only a subset can be written. Picture, description, interests, theme and timezone are collected today and would need core's own dedicated calls (core_user::update_picture, useredit_update_interests, useredit_update_user_preference). The confirmation page enumerates exactly what will be written — and the field picker already fixes this at the root: stop collecting what will never be saved.

A simplification the button unlocks

The submitted values are in the same request that renders the confirmation. Carrying them into the confirmation form as hidden fields makes a new table unnecessary for the offer: no privacy metadata, no retention, no test_table_coverage. And nothing is lost to a reload — a reload already hits the “already applied” short‑circuit (lib.php:146‑147), where no button is rendered at all. The audit snapshot remains a separate thing, written either way.

The plugin's CLAUDE.md says today that not saving is deliberate: “turning it into a real profile edit would let an enrolment form rewrite user records”. The objection is correct, and this proposal answers it point by point rather than removing it.

The attack that nearly got through

customtext4 is not plugin configuration — it is untrusted input. Core backs up customtext1..4 literally (backup_stepslib.php:692‑695), restore_instance() passes $data straight to add_instance(), and that one copies every key with no allowlist whatsoever (enrollib.php:2618‑2625).

In other words: whoever can restore a course — an ordinary teacher, on most sites — chooses the content of customtext4. And user_update_user() skips only keys that are not columns of {user}, so auth, suspended, policyagreed and confirmed would be written. A denylist is not enough.

And the same channel carries the switch. customint8 travels the same way: it is in update_instance()'s property list and add_instance() copies it unconditionally. A course restored into a category the attacker controls turns the profile write on by itself. Either the switch is a site setting — with no restore surface — or it goes into restore_instance()'s revalidation block beside customtext3 and is reset on every restore.

The rule: intersection, not negation

// classes/local/fields.php — on EVERY read, never only on the write
public static function resolve(\stdClass $instance, \context $context): array {
    $picked = fieldset::from_json($instance->customtext4);
    $pool   = self::pool($context);   // recomputed server-side: site setting ∩ live fields
    return array_values(array_filter(
        $picked,
        static fn($f) => isset($pool[$f->k]) && !in_array($f->k, self::DENY, true)
    ));
}

It is exactly what \core_user\fields::get_identity_fields() does at user/classes/fields.php:382‑387 with shortnames that have disappeared. The denylist stays, as a second barrier, with the minimum core itself keeps in update_user_record_by_id() — username, id, auth, mnethostid, deleted — plus password, policyagreed, confirmed, suspended, secret, trustbitmask. And restore_instance() revalidates customtext4 against the destination site, in the same block that already degrades customtext3.

The two locks today's form does not have

apply_form.php has no definition_after_data(), and the whole repository never mentions field_lock, hardFreeze or can_edit_profile. Today that is harmless because nothing is written. The moment it starts writing, a field locked by the auth plugin becomes writable.

LockSourceReproduced by
auth lock $authplugin->config->{'field_lock_'.$f} hardFreeze() and setConstant()

Both calls are load-bearing, not decoration

hardFreeze() erases every rule and makes exportValues() export an empty string; setConstant() lays the original value back over it. Copying only the first erases the locked value on the write — a silent failure, in exactly the opposite direction from the one intended.

“Render it read‑only” does not come for free

profile_field_base::edit_field() returns false and adds no element at all when is_editable() is false — and is_editable() is false exactly when moodle/user:editownprofile is missing, which is the same condition under which the design promised “everything read‑only”. The field simply disappears, while the confirm_<chave> checkbox stays on screen with nothing to confirm — and the “confirm before submitting” validation blocks a form the user has no way to satisfy.

Fix: the read‑only state is rendered by the plugin, with a static element carrying $field->display_data(); and confirm_<chave> is emitted only for keys that actually produced an element — by testing edit_field()'s boolean return.

Write order — core's own

// user/edit.php does it in this order, and for these reasons
get_auth_plugin($USER->auth)->can_edit_profile()                     // auth says "the profile is not edited here"
&& has_capability('moodle/user:editownprofile', context_system::instance())

$usernew = explicit allowlist;   // NEVER (array) $data
$authplugin->user_update($user, $usernew);      // otherwise LDAP/AD goes stale
user_update_user($usernew, false, false);       // $updatepassword=false, $triggerevent=false
profile_save_data($usernew);                    // fires no event at all
\core\event\user_updated::create_from_userid($USER->id)->trigger();  // one event, after everything

Without $triggerevent = false, the event would be born in the middle of the write. And profile_save_data() performs no authorisation check of any kind — whatever is on the object is written to user_info_data. All of the security on the custom-field side sits with whoever builds that object. The event, incidentally, carries ids and counts; never values — the log store is covered by no provider and no deletion request reaches it.

Reclassify at write time

Locks are UI only

user_update_user() never consults field_lock_*, and profile_save_data() performs no check at all. Core's only defence against a forged POST is setConstant() winning in exportValues() — and the rule “a locked field is not even rendered” removes exactly that defence, because there is no element to carry the constant. So: re-run the classification at write time and write only the keys classified editable, never the set of keys submitted. Plus require_sesskey() and a check that a non‑active user_enrolments row really does exist on that instance.

There is no core helper for “can this user edit this field right now”: the standard field lock is evaluated exactly once in the whole of Moodle, embedded in the profile form's definition_after_data(). The plugin has to write the predicate, and the config key for a custom field is auth_<auth>/field_lock_profile_field_<shortname>. Two details that bite: unlockedifempty's emptiness test is the loose != '' — a stored '0' counts as filled, and therefore locked, whereas !empty('0') would invert the decision; and auth_manual merges a legacy config component, so reading only get_config('auth_manual', …) misses locks the core form honours.

strictformsrequired: the reasoning runs backwards

It does not protect the write — it loosens it

The setting is read in exactly two places (formslib.php:3623 server side, :3641 client side), applies to addRule(…, 'required') on both sides automatically — a dynamic_form inherits it for free — and is identical on 5.1 and 5.2. There is nothing to “honour” beyond using the standard rule instead of inventing an emptiness test in validation().

But the default is off. With it off, ' ' (a single space) satisfies a required field — and that is what would go into the profile. The decision that actually matters is a different one and has to be taken separately: what does the writer do with a whitespace-only value? I recommend trim() before comparing and before writing, and treating the empty result as “not filled in”.

Collateral care: hardFreeze() erases the required rule along with all the others. And a required custom field of type checkbox does not use the required rule, so strictformsrequired never reaches it.

Erasing by accident

A submitted value is ignored only when it is absent from the form data — that is core's own boundary (edit_save_data() returns at if (!isset($usernew->{$this->inputname}))). An empty value is written, and erases. For checkbox and menu, any posted value — including '0' — is real; for text fields, '' is discarded only when a stored value already exists. This becomes a test, not a comment.

One last one on validation: profile_validation() walks every field that has data, not only the chosen ones. Its return has to be intersected with elementExists(), otherwise a forceunique field nobody picked blocks the form with an error that appears nowhere.

The backup: what travels, and under which key

Direct answer to your question

Yes, the enrolment method travels in both cases. The {enrol} rows are included unconditionally; “Include enrolled users” gates only {user_enrolments}.

But on restore the story is different: when the users are left out, process_enrol() converts the instance to manual and enrol_apply::restore_instance() is never called — no plugin element is processed at all. So: the audit trail travels only with users included. A test of the “back up without users and assert the audit trail did not come across” kind passes vacuously; it has to assert that no apply instance exists in the restored course.

On the gate itself: the earlier decision to use logs is still inverted — both defaults of logs are 0 and users gates logs, so the gate is strictly narrower and would bring the comments across without the record of the decisions. It stays in the users block.

A real contradiction between “travel in the backup” and “have its own retention”

The only attachment point an enrolment plugin has in the backup is the per-instance <enrol> element — which pushes the key towards enrolid. Except that a table keyed by enrolid is destroyed by delete_instance(), which runs on every instance deletion, not only on course deletion. That is the opposite of a trail with a lifecycle of its own.

Your decision, and both are defensible: (a) carry enrolid and courseid, and change delete_instance() to not delete the audit rows — documenting that the trail outlives the enrolment method; or (b) key by courseid and accept that the trail does not travel in the backup. Since you want both things, it is (a) — but it has to be written down, because it inverts the current cleanup behaviour.

Restore must not trigger a profile update

It does not, and the argument has to be about mechanism, not intent: restore_instance() always creates a new instance, {user_enrolments}'s unique enrolid‑userid key forces enrol_user() down the INSERT branch, and before_user_enrolment_updated is dispatched only by update_user_enrol(). No UPDATE, no hook, no task.

Two wrong sentences in the repository itself

The plugin's CLAUDE.md and the docblock at hook_callbacks.php:44‑47 both state that “the observer deliberately does not notify”. It does notify: it calls complete_approval(), which queues \enrol_apply\task\notify_approval (lib.php:249‑252). Fix both in the same commit — it is exactly the kind of sentence a reviewer would lean on to approve this design.

On a cross-site restore, the rows need annotate_ids('user', 'userid') and annotate_ids('user', 'decidedby'); when the mapping fails, the row is dropped, not written with userid 0 — an ownerless profile snapshot is not an audit trail, it is loose personal data.

Deletion: “when the recycle bin is emptied” does not exist as a state

With the recycle bin on, the course is deleted in full, immediately. The recycle bin keeps only a zip of the backup plus a row in tool_recyclebin_category; emptying it deletes that file and that row, and nothing else. Core's own test asserts that the course row is gone the instant delete_course() returns. So both branches of your decision collapse into a single moment: course deletion.

The hole: plugin disabled

enrol_course_delete() calls delete_instance() only for enabled plugins (enrol_get_plugins(true), enrollib.php:1177,1190) — and then deletes the enrol and user_enrolments rows anyway (:1194‑1196). If enrol_apply is disabled when a course is deleted, the rows are orphaned permanently, with no key left to find them by. No error, no warning.

Hence the courseid column on the new table: it is the only key that survives as far as the course_deleted event, which fires after the course, the context and the enrolments are already gone. The cleanup lives in two places, and both are needed:

RouteCoversDoes not cover
Primary

The observer normally finds zero rows, so its test needs a control row in another course that has to survive — otherwise it passes without exercising anything. And a new db/events.php requires a version bump to register.

A correction to the sentence “deleting the course deletes the data”

It does not: it deletes the live rows. A full copy stays inside the recycle bin's zip until that backup is removed — and the cleanup task returns immediately when the recycle bin is disabled, which leaves every existing item stranded indefinitely. Worth saying so in the documentation instead of promising the opposite.

The privacy provider is not a cleanup mechanism: core never calls delete_data_for_all_users_in_context() when deleting a course or a context — only tool_dataprivacy does, by retention or by request. It remains a separate obligation, and now has to cover two roles, the applicant and whoever decided.

A configurable lifecycle driven by a scheduled task — yes, it makes sense

It does, and there are three precedents in the fleet plus one in core. A days setting with 0 = keep forever, a daily scheduled task in db/tasks.php. But with two corrections that decide whether it is honest:

An audit row must not outlive the course carrying personal data

contextlist::add_from_sql() wraps every provider query in a JOIN against {context}, and the course context is destroyed before course_deleted fires. A retained row is therefore invisible to the data subject's access request and unreachable by a deletion request — silently.

Fix: act in the hook \core_course\hook\before_course_deleted, which is dispatched while the context is still alive — not in the course_deleted event. And there: either delete, or pseudonymise properly — zero out userid and decidedby and discard the snapshot, keeping only dates and status. Anything less than that leaves personal data nobody can reach.

Sweep by timecreated, not by timedecided

An undecided row has timedecided = 0: a sweep on that column would keep exactly the abandoned applications forever. And the task has to run in chunks, with a time budget, logging and skipping a bad row — never throwing: a failure applies exponential backoff up to 24 h and a single poisoned row freezes the whole retention.

fleet correction The ~/dev/CLAUDE.md rule that “a throwing ad‑hoc task is retried forever” is wrong on both branches: attemptsavailable is decremented, queue_adhoc_task() sets it to 1 when retry_until_success() is false, and exhausted rows are deleted after four weeks. Worth fixing that sentence there, since it guides the whole fleet.

06 — Reporting

A report in the course, a datasource at the site

Core restriction

A custom report cannot be scoped to a course. The contextid of the persistent is born in the system context and the creation form offers no context at all; set_condition_values() writes to the shared record, so there is no per-viewer condition. The “embed a custom report in the course page” route does not deliver what was asked for.

The answer is to ship both surfaces, which is what the request describes once you look closely:

  • system_report course_applications — created with context_course::instance($course->id). It does not go through $CFG->enablecustomreports: on a site that has turned custom reports off, this one keeps working.
  • datasource applications — discovered automatically by the class map from the path and the namespace alone. There is no db/reportbuilder.php; what there is is the need to bump version.php so the map is rebuilt.
can_view() is the whole gate — not “defence in depth”

The temptation is to validate everything in report.php before creating the report. Except that report.php does not run on page 2: every sort, filter and page re‑instantiates the report through core_reportbuilder_retrieve_report, which receives source, context, component, area, itemid and parameters straight from the client, calls only validate_context() and then require_can_view().

So can_view() has to carry everything: assert that $this->get_context() is a context_course and require enrol/apply:viewreports on it. And neither get_parameter() nor the persistent's itemid may scope the query — the base condition comes from $this->get_context()->instanceid and from nothing else.

The new capability needs more than one line

enrol/apply:viewreports grants access to the frozen profile values of every applicant in scope. db/access.php today declares no riskbitmask on any capability — defensible for config and manage, not for this. Declare RISK_PERSONAL and state the archetypes explicitly (manager only, if the report carries profile values): inheriting the neighbours' editingteacher default hands the report to every editing teacher by omission.

Report Builder traps between 5.1 and 5.2

The plugin's waiting list collides with a core constant that means something else, and the three-option filter never reaches those rows.

More: every parameter bound in the report's SQL has to come from database::generate_param_name() (validated against /^rbparam[\d]+/); column names are PARAM_ALPHANUMEXT and unique, on pain of coding_exception; lang_string validates in the constructor, inside initialise(), so every string has to exist before the first PHPUnit run (CI runs --fail-on-warning); and the callback that prints the JSON has to keep its first parameter untyped, because datasource_stress_test_columns_aggregation() applies every compatible aggregation and groupconcat re-applies the callback value by value.

The user entity to reuse is core_reportbuilder\local\entities\user — there is no user entity under core_user on either branch. The other two are core_enrol\reportbuilder\local\entities\enrol and core_course\reportbuilder\local\entities\enrolment.

Asynchronous download

Recommended order

Synchronous first — set_downloadable(true) costs one line and covers most courses. The asynchronous path comes afterwards, gated on a row threshold. That way the slice delivers value before paying for a task, a message, a file area, cleanup and pluginfile.

The hole in the asynchronous path is failure, not success

task_indicator looks the task up with $includefailed = true by default. An exhausted task survives four weeks in the queue, while the progress record is deleted after 24 h — result: the page keeps saying “your export is in progress” indefinitely, with no bar and no final state. And retry_until_success() has to be overridden to false: with the default, a task that fails after writing the file either collides on the same pathnamehash (permanent failure, 12 attempts, backoff up to 24 h) or — if the name carries a timestamp — leaves up to 12 orphan copies, each firing its own notification.

07 — Cohort

“Cohort members only”

customint5 is free and it is the same column enrol_self uses — same vocabulary: 0 for no restriction, a real id, or the -1 sentinel on a restore to another site. No XMLDB change: the column already exists on every site.

The check goes in allow_apply(), not in enrol_page_hook(). It is the method every present and future caller goes through, and the one the test_allow_apply_respects_instance_state test already exercises; leaving it in the hook would make allow_apply() blind to the restriction.

Three things to copy verbatim

// 1. The FOUR arguments. $limit defaults to 25 — without the fourth, the picker
//    silently truncates on a site with many cohorts.
$allcohorts = cohort_get_available_cohorts($context, 0, 0, 0);

// 2. No cohort available: hidden + constant. This is NOT defensive noise —
//    update_instance() only copies the property when isset($data->$key), so
//    omitting the element makes an existing restriction impossible to remove.
$mform->addElement('hidden', 'customint5');
$mform->setType('customint5', PARAM_INT);
$mform->setConstant('customint5', 0);

// 3. Cross-site restore: the -1 sentinel, not 0. Zero would REMOVE the restriction — failing open.
if (!$step->get_task()->is_samesite()) { $data->customint5 = -1; }
Two things NOT to copy

The validation. enrol_self treats customint5 as PARAM_INT and nothing else (lib.php:1123) — no check of existence, visibility or membership of the list offered. Copied verbatim, that is a hidden-cohort name and membership oracle for anyone holding enrol/apply:config. Copy enrol_cohort’s guard instead: array_diff against the option keys → get_string('invaliddata', 'error').

The “keep it selectable” fallback. When the stored value is not in the available list, enrol_self re-reads the cohort with a raw get_record — which ignores the parent‑context and visibility rules cohort_get_cohort() applies — and hands the real name to the form. Exempting the stored value would only be safe if it could only have got there through the form, and it cannot: customint5 also arrives by restore, through the same allowlist-free copy. Put the stored value through cohort_get_cohort($id, $context) as well, and when that refuses, keep the option selectable with the label get_string('unknowncohort', 'cohort', $id) — never with the raw name.

A third enrol_self detail that is not copied either: when the cohort has been deleted it returns null, and the enrolment method disappears from the page with no message to anyone. Here a real string has to come back — this plugin’s enrol_page_hook() would pass null to notification() and paint an empty red box.

10 — Prior art

What to take from enrol_gapply

Verdict

Learn from it and reimplement — do not copy code. It is worth a great deal as a requirements document and as a catalogue of security anti‑patterns. As a source of code, almost nothing is portable: 3.3 MB of bundled DataTables + JSZip + Select2 (90% of the JS+CSS weight against 188 KB of PHP), jQuery in 4 of the 5 own modules, zero tests, no backup, no event on any write, and an unauthenticated pluginfile.

Anti‑pattern catalogue — for our own review checklist

  • Unauthenticated file disclosure. The pluginfile callback reaches send_stored_file() with no require_login, no enrolment check, no capability check and no ownership check. It is exactly the trap in our §6 about the generic branch of file_pluginfile — now with a real case to cite.
  • Attachments travelling to Google and Microsoft. The viewer falls back to docs.google.com/viewer?url=… and view.officeapps.live.com. Added to the item above, that is a working exfiltration path, not a theoretical one.
  • Leak in the profile summary. It loads the custom fields and prints them all, with the management capability as the only barrier — no is_visible(), no viewalldetails. It is the defect our §2 design of “frozen visibility, live capability” exists to prevent.
  • Status vocabulary in char(255) assembled by concatenation and read back with a dynamic get_string() — forbidden by the fleet standard.
  • Duplication solved by prohibition: can_add_instance() prevents a second instance in the course. It gets it wrong twice — it forbids the use case and does not even close the hole, because restore and course copy go around it.
  • groups_add_member() without the component argument — the defect we have already fixed and that the plugin's CLAUDE.md documents.
